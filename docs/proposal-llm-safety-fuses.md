# 内核提案：主循环 LLM 安全熔断三件套 + daemon 状态机自愈

> 状态：提案（待内核评审）· 2026-09-18 立项 · 源头：2026-09-17 全天实测四起事故
> （f39e 565 轮纯文本循环 / d80a 跨会话重确认循环 / qwen 思考跑飞 600s 超时 /
> f39e+a06a daemon 状态机卡死），管理员指示「给内核写一个建议，让内核改」。

## 背景：四起事故，四个内核缺口

| # | 事故（实测） | 内核缺口 |
|---|---|---|
| 1 | agent-1575（qwen 27B 主循环）：上下文仅 **5,640 token** 的请求，600s 超时——llm-2 现场日志 40-70 tok/s 连续生成 10+ 分钟（≈3 万 token 思考链跑飞） | 主循环**不传 max_tokens**，思考模型「生成到自然结束」无上限 |
| 2 | f39e（spark 4B 主循环）：12:12–12:57Z 单会话 **565 轮纯文本**「我准备好了」循环，无一次工具调用；外部强令信后仍只口头应承不执行 | 纯文本续会话无熔断：内核只有「每会话一次」的文本提示，无硬闸 |
| 3 | d80a（spark 4B 主循环）：每 120s 一场呼吸、**每场重新确认一遍已办完的「载体重启通知」**，carry 上下文逐场膨胀（9.4k→12k→…） | 信只注入一次（mailbox drain 一次性），但 carry 把**上次会话的完整对话记录**整个传给下一场（agent.py:212/228）——信作为对话里的一条 user 消息被逐场重放 |
| 4 | f39e、a06a 各一次：daemon 状态 = `running_session`，但最后会话已结束数小时、8 个门铃无人响应 | daemon 状态机卡死无自愈（看门狗只判进程死，不判状态机死） |

## 方案一：主循环 max_tokens 上限（BrainSpec 加字段）

**改动**（三处，行为向后兼容）：
1. `BrainSpec` 加 `max_tokens: int | None = None`；
2. config 解析读 `[brains.X] max_tokens`（None = 不传，与旧版逐字一致）；
3. `OpenAICompatibleBrain.chat()` 请求体 `if spec.max_tokens: body["max_tokens"] = …`。

**配法**：池里 qwen-local / qwen-local-2 / spark 条目配上限（如 16k），思考 token
与正文同受钳制——治「5.6k 上下文跑飞 3 万 token」；power 脑不配（保持无上限）。

**影响面**：所有 agent 主循环。未配置的脑行为不变；配置的脑生成到上限即截断
（finish_reason=length，与今日 llm-2 的 947 个 length 请求同形态）。

## 方案二：连续纯文本强制收尾熔断

**改动**：会话循环内计数「连续无工具调用轮」；N≥2 时内核在下一轮开头注入
**强制提示并预填 end_session**（N=2 注入强提示、N=3 机器直接代写 end_session
工具调用结束会话——最后一档不依赖模型执行力）。

**依据**：f39e 事故中模型「口头应承、不调工具」——纯提示级熔断对它无效，
必须到 N=3 机器代收尾才成立。

**影响面**：正常 agent 极少连续 3 轮纯文本（工具调用是主循环常态）；误伤面 =
「有意连续多轮纯文本对话」的形态，与内核「纯文本不结束会话」的既有语义一致，
不冲突。

## 方案三：机器不重放「机器注入的信件」（carry 信件消息会话级作用域）

**机制复核（2026-09-18，管理员指出）**：信件注入本就是一次性的（mailbox drain
只在会话开头清一次），问题不在注入——在 **carry 把上次会话的完整对话记录整体
传入下一场**（agent.py:212 `initial_messages: 接续上次会话的对话记录` + :228
全文拼接），信作为对话历史里的一条 user 消息被逐场重放。本方案针对的是这个
carry 记录，不是注入。

**原则约束（评审先行）**：机器**不得替 LLM 写「已办/未办」**——「有 assistant 轮
≠ 已办成」（f39e 事故实证：口头应承、工具未执行），机器做这个判断就是往大脑
记忆里植入语义，违反「机器不干预大脑认知」原则。本方案只做**机器侧的机械清理**：
信件消息是机器注入的，机器可以决定不把它重放进下一场，不写任何标记。

**改动**：`mailbox.drain()` 注入的信件消息（`【标签 时间】信文` 形态的 user 轮）
在 end_session(carry=true) 时**不进入 initial_messages**——当次会话内照常全文
在场，跨会话一律不重放原文。已办与否的记忆完全由 **LLM 自己写的 final_summary**
承担（它本就被 carry 或落盘）。

**配套（机器只提供事实入口，不提供判断）**：下一场开场白附一行事实提示——
「历史来信原文见 data/mailbox_log.jsonl，需要时自行查询」——机器指路，不评价。

**影响面**：d80a 类「重确认已办通知」的病灶移除（刺激源不再跨会话重放）；4B
脑不会因「看起来像待办」的历史信反复回应；正常 agent 对历史信的依赖改走
mailbox_log 自查（比 carry 原文更可靠——那是完整台账）。

## 方案四：daemon 状态机自愈

**改动**：daemon 心跳内判「`running_session` 但 `current_session` 的会话文件
已终态超过 T（如 5 分钟）」→ 视为状态机卡死，自动 `daemon restart`（或状态机
归零重排）；门铃队列保留（重启后照常消费）。

**依据**：f39e/a06a 两次卡死都是「API 活着、状态机冻住」，现有看门狗只判
进程死活，测不出这类。

**影响面**：daemon 内部自愈，agent 无感；仅当状态机误判卡死（理论上会话确实
在跑但文件未写）时触发重启——以「会话文件已终态」为硬判据，误触发概率低。

## 回滚与验证

- 全部改动带版本号（v2.7.46 候选），单字段开关（None 不传 / N=0 不熔断），
  行为向后兼容；
- 验证三件套：单元（selftest 补四项用例）+ 试点 agent（f39e/d80a 复测原始
  事故路径：投信→重确认？纯文本 3 轮→机器收尾？思考跑飞→钳到上限？）+
  全队灰度（照 kernel-upgrade.md 流程：先 1 台观察半天再批量）。
