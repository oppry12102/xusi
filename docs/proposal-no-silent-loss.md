# 四处静默丢事修正——机器不得对大脑说谎（内核修改建议）

> 状态：**建议（待评审）** · 2026-09-26 · 源头：代码审查 `8b2a954..HEAD`（v2.8.12–v2.8.48，36 提交）15 条确认发现之 1–4 号
> 本文回答三件事：①四处问题各是什么（附复现路径）；②每处怎么修；③哪些取舍是明知的。

## 0. 总览：四条同一族

15 条确认发现里 1–4 号是同一族：**机器对大脑说谎或静默丢事**。其余 11 条是
契约漂移/测试假绿/死代码（另稿）。这四条单独成稿，因为它们违反项目自己的哲学
——「机器只报事实，判断归大脑」——报假事实的机器比没报的更危险；静默丢事则
让大脑失去做判断的材料。

## 1. 微信参考实现吞消息（seed.py:1513）

### 1.1 现状与复现

`_handle_inbound` 尾部：

```python
text = extract_message(m, mid)
if not text.strip():
    return
mailbox.post(text, sender="admin·微信")
```

`extract_message` 返回空的路径至少三条：

- 媒体 item 缺 `encrypt_query_param`/`full_url` → `continue`（1082-1083、1103-1104，
  不 append 任何占位）；
- 未知 item type（链接卡片等）无分支；
- 语音既无媒体又无转写（1098 只有 `elif note`）。

此时：不投 mailbox、不落 log、不按铃；而 message_id 在 1489-1495 已先入 seen
（512 上限）——同一条消息重投也被判重复。**永久静默丢失**。

8b2a954 的种子里这恰好是一条血训（坑表 #16：「if not text: continue 吞掉媒体
消息（主人发图石沉大海、日志无痕）」+ 不变式·媒「即使提不出文本也必须投占位，
绝不允许吞掉整条消息」）。v2.8.18（7211994）减负时把坑表整段删掉，v2.8.39
（882b28d）合成参考实现时又把「提不出文本就丢」写回了代码——血训在正文里已
无处可查，代码却重犯了它。`extract_message` 自己的 docstring 还留着同族教训
（「一条媒体异常曾让整条消息——连同文字——无声丢失」），原则到了整条消息级
反而失守。

### 1.2 修法

原则：**收信路径不许静默 return**——提不出文本 ≠ 消息不存在。占位本身就是诊断。

1. `_handle_inbound` 空文本分支改投占位，之后照常走 post / log / 按铃三件套：
   ```python
   text = extract_message(m, mid)
   if not text.strip():
       types = [i.get("type") for i in m.get("item_list") or []]
       text = f"[消息] 内容无法解析（mid={mid}，item types={types}）"
   ```
2. `extract_message` 里媒体的 `continue` 改成 `parts.append("[图片]（无下载参数）")`
   等占位，未知 type append `[item type={t} 未支持]`——与既有「单条媒体失败降级
   为一行提示」同口径。
3. 不变式回收入正文一句话（恢复 8b2a954 口径）：「即使提不出文本也必须投占位，
   绝不允许吞掉整条消息（不变式·媒）」。
4. 备选加固：seen 记账移到 `mailbox.post` 成功之后（消息失败可重投）。主修
   1–3 已闭环，此项可选。

这不是新设计：坑表 #16 就是 e2e 实例评审蒸馏出的既有决定，本次是把它找回来。

## 2. 门铃「已投递上口」是谎言（daemon.py:137）

### 2.1 现状与复现

同批 drain 出来的 N 条便签，投递通道只传最新一条（`notes[-1]`），其余 N-1 条
从未送达大脑；文案却标「（已投递上口）」。v2.8.29（18b3ef7）架构收拢时删掉了
旧版恢复路径「全文在 data/facts.db 的 bell 行自第 N 行起，读不读由你」，docstring
（117-118）却没同步，仍承诺「其余便签给事实指针」——代码与自述互相矛盾；
v2.8.48（05a60b4）「只说投递不说处理」的措辞修正又在这之上补了「已投递」断言。

实测（三条 pending 铃 n=2/3/4）：开场白「此前还有 2 次（已投递上口）」，随后
会话中途 drain 返回 []——A/B 只存在于账本、从未送达。大脑据此认为只有 C 是
新事，A/B 的完工/死亡信息被静默忽略；旧版大脑至少有指针可自行恢复。

### 2.2 修法

两个方向，推荐①：

① **改文案为真**（最小改动）——去掉投递断言、恢复指针：

```python
if len(notes) > 1:
    more = (f"；此前还有 {len(notes) - 1} 次（未投递——全文在 "
            f"{get_config().data_dir}/facts.db 的 bell 行自第 {notes[0].get('n')} "
            f"行起，读不读由你）")
```

同时把 docstring 的承诺与文案对齐。v2.8.48 的意图（机器只说投递、不说处理）
是对的，错在把「没投递」写成了「已投递」——修的是事实，不是方向。

② 真的投递：把 N-1 条便签也进开场白（各 200 字截断）。违背「铃只传最新一句」
的设计意图（防 bell 风暴撑爆开场白），不推荐。

另注：指针路径要用正确的 data_dir 口径——同批审查发现 #6 指出三处 agent 可见
路径被改写成 `~/data/…`，本机布局下账本不在那里（见 §5 关联项）。指针指一个
不存在的文件等于没有指针。

## 3. 状态块截断丢关键行（daemon.py:417）

### 3.1 现状

`_STATE_CAP=1500` 超限时只保 `lines[0]`，其余全换成一句「完整状态用 facts_tail()
读」。但：

- 生产者顺序是 0B 自检 → 残留 → 铃 → 眼睛 → 指针，`_finalize_state` 里
  `[mail 未读]` 永远最后 append（404）——状态一多，`lines[0]` 是最旧的自检行，
  大脑看不到是谁叫醒它、有没有未读信。
- 0B 残件行只进状态块和 stderr（478-481），从不落账——`facts_tail()` 指针救不回。

### 3.2 修法

① **保尾不保头**：状态块的价值是「此刻为什么要醒」，最有信息量的是最新追加的
行。超限时保留最后 K 行（mail/铃/会话优先）而非 `lines[0]`。

② **0B 残件落账**：`facts.append("residue_0b", …)`，状态块只留指针——与「内容
进开场、历史走工具」的既定哲学一致，消灭「只有 stderr 知道」的孤本。

③ 备选：封顶从「整块丢弃」改成「逐行截断」（每行 60 字），更温和但保尾已
覆盖主要损失。

建议 ①+②。

## 4. svc 看护静默整体失效（svc.py:53）

### 4.1 现状与复现

v2.8.28（1405f7e）新引入的 svc 看护，三条路径全是静默失败：

- `_read`（30-34）把损坏 JSON 当空表：register 在其上读改写会**抹掉其他登记**；
  `svc list` 打印「（登记表为空）」退出 0，与真空表不可区分。
- 登记表若是 JSON 列表，register 的 `d[name] = …` 直接 TypeError traceback。
- 写入非 dict 值（如 `{"api": "port:8404"}`）后 `probe()` 里
  `(spec or {}).get("health")` 抛 AttributeError → daemon `_svc_probe`（428-431）
  裸 except 吞掉——**看护整体消失且无任何报告**。

实测：干净登记表响 2 声掉线铃；掺一个坏值响 0 声且 `_svc_state` 保持空。夜间
服务死掉再也不会有铃，也没有任何地方说「看护已停」。daemon.py:431 注释
「登记表读坏由 CLI 侧可见」不成立——CLI 同样静默。

### 4.2 修法

原则：**损坏必须可见，坏项不得拖死看护**。

1. `_read` 损坏时：原文件改名备份 `svc_registry.json.corrupt-<ts>`（保留现场），
   stderr 报告，返回 {}。备选：直接 raise 由调用方处理——但 CLI 与 daemon 两个
   调用方都要接，改名备份 + 空表更省。
2. `register`/`unregister` 读回非 dict → 返回
   `{"ok": False, "error": "登记表损坏：已备份到 …，未写入"}`，不写不抹。
3. `probe()` 跳过非 dict 项，但掉线按铃带原因（note 含「登记项格式错」）——
   坏项可见，好项照常探测。
4. daemon `_svc_probe` 的 except 分支至少按一次「svc 看护失效」铃 + stderr
   （去重：报一次直到恢复），替代现在的静默 return。

## 5. 范围与验收

- 全部机器面，不涉及种子协议形态的再决策（第 1 条只是恢复一条既有不变式）。
- selftest 补四组断言：
  1. `extract_message` 全 item 不可解析 → 返回占位而非空串（钉住不变式）；
  2. 多铃开场白含「未投递」+ 指针行号，不含「已投递上口」；
  3. 状态块超限时 `[mail 未读]` 行仍在（保尾）；
  4. 坏登记表：register 返回 error 且原表字节不变；probe 含坏值不抛、好项照常探测。
- 关联项（可同批）：#2 的指针路径与发现 #6（`~/data` 口径，mailbox.py:70 /
  tools/shell.py:142 / tools/xmem_tools.py:127）同批修；#3 与发现 #14
  （daemon.py:407 上下文 x/y 死代码）同区域，可顺带确认。
