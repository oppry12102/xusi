# 提案：管理员信与同伴信统一收信面（一个信箱、一条游标、一个铃）

- 状态：**已实施**（2026-11-25，commit 4fb86ac；内核零改动确认）。实测：睡眠 11.7h 的 5290，新路径投信 4 秒后 early_wake "by":"mail"
- 提出与管理面分析：管理员会话（fad0 排名深挖引出）
- 证据样板：本机 agent-5290（facts 行号 64135–64245）

## 一、问题

管理员邮件（`agentops.mail()` → facts.db mail 行）存在两类失效，且**第二类是静默丢失**：

1. **睡着不醒**：员睡眠期间 mail 行落账，无任何唤醒动作，信要等下次自然呼吸才被看到（延迟，尚可）。
2. **会话中静默丢失（严重）**：mail 行落在员**会话进行中**时——本轮不注入、会话结束游标推过该行——信从此不再进入任何上下文窗口，**永久丢失，无人知晓**。

### 证据链（5290 案，facts 账逐行）

| 时刻 (Z) | 行号 | 事件 | 含义 |
|---|---|---|---|
| 09:05:49 | 64135 | `bell`（同伴 185b 来信） | 同伴信有铃 |
| 09:05:50 | 64136 | `early_wake` "by":"bell" | 铃→立即惊醒 |
| 09:05–09:28 | 64137–64204 | 会话 090550Z 共 33 轮 | 处理同伴信 |
| **09:16:19** | **64177** | **`mail`（管理员评审邀请）** | **无 bell、无 early_wake** |
| 09:18–09:28 | 64178–64204 | 同会话第 21–33 轮 | 会话未重读账本，评审信未进任何一轮 |
| 09:28:03 | 64204 | `session_end` | 游标越过 64177——**信被永久跳过** |
| 09:31:08 | 64206 | `early_wake`，`new_rows:1` | 下一会话基线已在 64177 之后 |

会话文件（093108Z.json）核验：全篇无评审相关内容。该信至今未被 5290 读到。

### 同期旁证

同一批评审邀约（09:16Z 投递）：六名员秒回~时回（**均为醒来或恰逢会话起始窗**）；四名员零响应（**信落在其睡眠/会话中段**）。到达质量随机——这就是主人观察到的「发管理员邮件，智能体不醒」。

## 二、根因

### 2.1 双通道不对称

| | 同伴信 | 管理员信 |
|---|---|---|
| 通道 | 收信服务（inbox_server）→ inbox.jsonl | 管理面直写 facts.db |
| 铃 | 收信服务自己敲（facts `bell` 行） | **无人敲** |
| 消费游标 | inbox 专属行游标（`inbox_lines_read`） | **facts 流水游标（会话结束推到尾）** |
| 丢失性 | 不丢（文件在、专属游标只进不跳） | **会话中落必丢** |

同伴信的铃是**员的收信服务**在收到 POST 时自己敲的；管理员信绕过收信服务直写 sqlite，没有任何人敲铃。

### 2.2 本质：投递骑在了「可丢弃游标」上

facts 流水游标为**上下文馈送**设计（llm_usage、session_end 等过路账——会话结束推到尾、永不回头），语义是 best-effort 可丢弃。而 mail 行是**投递语义**（绝不能丢）。两种语义共用一条单调游标 → 投递语义必然在「行落账于会话中段」时被吞。

> **规律：绝不能丢的投递，不能骑在可丢弃的流水游标上。**

v2.9.32 的设计声明「账本行已同时完成投递与唤醒」（内容在哪，信号在哪）只在「员醒着且轮边界重读账本」时成立；5290 案证明两个前提都会塌。

## 三、定案方案：管理员信就是一封同伴信（统一收信面）

**`mail()` 改为把信投进员的收信面（inbox.jsonl，sender=admin）+ 敲铃；facts 的 mail 行降级为审计留档副本，不再承担投递。**

- 内核**零改动**：它本就按专属行游标读 inbox.jsonl 的每一封信，管理员信（sender=admin）与同伴信同形同权
- 三类失效一次全治：

| 病 | 治后 |
|---|---|
| 睡着不醒 | 铃照敲，early_wake 现成 |
| 会话中静默丢失 | 信在 inbox.jsonl 有专属游标，只延迟不丢失，下轮必读 |
| 双通道双语义 | 一个收信面、一条游标、一个铃——「唯一通信通道」的文档首次成为事实 |

### 设计原则（为什么这是本质修法）

1. **投递不可骑可丢弃游标**（本提案 §2.2 规律）
2. **管理员与同伴是同一种发信人**——拆掉「两种投递语义」的概念本身，此类 bug 从此没有存活空间
3. 贴合舰队自家哲学：「文件即一切」（信在文件里，丢不了）、「零信息纪律」（管理面不再预测员何时醒——信放在它必读之处，员自己决定何时读）

## 四、已否决的备选

| 备选 | 否决理由 |
|---|---|
| A. `mail()` 落账后补敲 bell 行 | 治「睡着不醒」；**不治会话中丢失**（bell 行同样被流水游标越过） |
| B. 内核轮边界重读账本新增行 | 治会话中丢失；但双通道双语义仍在，且为内核改动（应攒入下版而非单发） |
| C. 发信后核验消费、未消费重发 | 过渡期缓解可用；永久化=把投递可靠性寄希望于重发运气 |
| D. 网关/管理面代改请求参数类 | 越权，毁归因（同 max_tokens 案教训） |

## 五、实施清单

1. `agentops.mail()`：投递目标改 `workspace/inbox.jsonl`（sender=admin）+ 追加 facts `bell` 行（note「管理员来信已落账」）；facts `mail` 行保留为审计镜像
2. `mailbox` API（box=inbox 展示）：读源切 inbox.jsonl（或维持 facts 审计镜像展示，标注「审计副本」）
3. 兼容：旧 facts mail 行为历史，不迁移；员的收信服务无需改动（admin POST 与同伴 POST 同形）
4. 停止态员：inbox.jsonl 在共享卷上直append 可用；员下次 start 照常按游标读——停止态不丢信
5. selftest：新增「mail 落 inbox + bell 行成对」断言；新增「会话中投信→下一会话必读」场景档

## 六、验收标准与实测

- **睡眠员投信**：✅ 已实测——5290 睡 11.7h，新路径投信 4 秒后 `early_wake "by":"mail"`（facts 行 64246-64248）
- **会话中投信**：信落 inbox.jsonl（专属游标，不要求本轮注入）→ 下一会话首轮必读。原 5290 案的验收口径「当前会话下一轮必读」按门铃权威语义修正为「下一会话首轮必读」（门铃文档：会话中途已到的行不追醒，时效归 sleep_seconds 与收尾纪律）
