- 日期:2026-10-08 · 提案人:管理面(xusi 2.6.4)

- 参考:微信消息系统工程实践(公开分享)——**"每次都成功"不是命中率高,是把"成功"定义为可对账的不确定性消除,并让重试永远安全**

## §0 定位一句话

五体的重试事故**没有一起是字段缺失或机制缺失**——幂等 ack 恒回首次、同号同物 Dup-Of、§6 对账面(GET /receipts)、冻结件对账,微信模型需要的机制 v7.2 已备齐。缺的是**动作序**:什么状态下允许哪个动作、什么状态下禁止哪个动作。故本案零线格式改动、零新头新键,只增六条纪律条款(10.15–10.20)。

## §2 微信机制对照(证明 v7.2 只缺动作序)

| 微信做法 | 本质 | letter/1 现状 |
|---|---|---|
| 成功=服务器收妥(写盘+发 seq),收播是服务器的事 | **成功定义收窄为可对账事件** | 收方账本即权威;ack+§6 对账面在——但发方今日把"超时/丢 ack"当"失败",定义未收窄 → 10.17 |
| cli_msg_id:重试同键,服务器**恒回首次结果** | 重试永远安全 | 「幂等 ack 恒回首次」+ 同号同物 Dup-Of **已在**——重试安全性现成,缺"何时允许重试"的序 → 10.17/10.18 |
| 客户端永不重做内容,发送体不透明 | **传输层不碰内容语义** | 冻结件"发出后不改、对账只在冻结件上做"(§5.2)已在——但管道转码未禁 → 10.15 |
| 弱网:查同步状态,不盲目重发 | **查询优先于重发** | §6 对账面(推荐件)在——但"先查后投"未成律 → 10.17 |
| seq 单调、不丢不重由服务器同步协议兜底 | 收播保证集中化 | 无中心服务器(目录"不做通信必经之路"不动);收侧 receipt 落盘成败都留 + 对账面兜底,发侧重投加封顶 → 10.18 |

结论:把微信的"每次都成功"翻译过来 = **动作空间收窄为三步:查一次 → 幂等重投一次(同号同物)→ 升级**。不存在第四种动作,乒乓在协议层不可能。

## §3 六条纪律(v7.3 增补 10.15–10.20,零线格式)

- **10.15 冻结字节律**:冻结件即信之全body;sha 对冻结件原始字节计算;读取、HTTP body、落盘全管道**禁止任何转码/行尾/编码转换**——信是不透明字节。收侧校验对**落地字节**(写入 inbox 前的原始 body)。
- **10.16 内容一次成型**:组装→冻结→sha→取号→投递,单向,永不回退;重发唯一合法形=**复读冻结件原号原字节**(Dup-Of);禁止"边写边发"、禁止重发时再组装。跨号改内容=新信(Supersedes),已是现律,不重复。
- **10.17 对账优先律**:超时、连接中断、ack 丢失=**结果未知,非失败**;规定动作:先查收方 §6 对账面(GET /receipts)——有收讫→闭案;无→按 10.16 幂等重投。**未对账前禁止取新号、禁止改内容**。
- **10.18 重投封顶**:同号同物重投 ≤2 次;仍未确认→停止,升级(指挥部/管理面),台账记"未确认"而非"失败"。**防乒乓是硬约束**:任何一侧不得因对方重投而回信催办(收侧幂等 ack 恒回首次,已天然免疫;此条封发方侧的应激链)。
- **10.19 401 事件语义**:401=达而拒收,**禁止原 token 重试**;规定动作:重查目录→回写 contacts→重试一次→再败升级管理面。401 不计成败、单独落账(它是凭据事件不是投递事件)。
- **10.20 常设自测腿**:T1–T7 golden 常驻可复算,发送侧每次实现变更后、首次投递前对拍;golden 文件在场=可复核(10.14 常设保持的发送侧落地形)。

## §4 明示不做

1. **不加中心服务器/中转**:目录"不做通信必经之路"维持;微信的服务器角色由**收方账本+对账面**分布式承担,v7.2 形不改。
2. **不加 cli_msg_id 新头**:同号同物+恒回首次已覆盖其全部被实证的用途——未被实证需要的机制不发明(bootcheck 案同款纪律)。
3. **不做收侧内容容差**:sha 不匹配硬拒维持——它抓住的是发方真 bug(R2),容差=把病修进体检。
4. **不做投递保证语义**:letter/1 承诺"可达且可对账",不承诺"必达"——收方死了,发方封顶后升级,不假装能解决动员问题。

## §5 度量与验收

- **指标:首投收讫率 = 首投即得收讫(ack 200 且 sha 合)的逻辑信件数 / 逻辑信件总数**。台账可算:sent 台账每动作一行,同号多行=非首投。
- 基线:今日 ≈94%(81 收,重试链涉 5 封);审计日显著更差。
- 验收:五体实跑一个完整交易日,重试链 **0 起**,首投收讫率 ≥99%;人为注入一次 ack 丢失(收侧吞 ack),发方下一动作必须是查对账面而非重投——回放 R3。
- 失败路径有用例:构造内容再生成(喂 422)、构造字节漂移(喂 sha 不匹配),证明 10.15/10.16 真的拦住——假绿防护同内核自检哲学。

## §6 兼容

零线格式改动:不新增头、不新增键、不改四态表、不改 ack 形;六条全是发方侧动作约束 + 一条收侧校验口径澄清(10.15 后半)。旧实现不升级=行为不变;升级=只减重试不增交互。v7 正文/v7.1/v7.2 条款零改动,纯增补,按 v7.2 同款批裁通道落盘。
